Kestrel requires an automated verification loop spanning C firmware, RTL, compiled .eff programs and physical hardware. These are desired capabilities, not claims that the present tools satisfy the complete loop.

- Maintain a useful C test suite and a set of simple, automatically runnable Verilator RTL tests.
- Provide a lightweight simulator of the actual DSP with one pipeline, so agents can write .eff descriptors, execute them and inspect results in an iterative loop.
- Also provide a full Verilator simulation of one DSP pipeline to verify written .effs against the RTL. The lightweight model and RTL simulation serve distinct purposes; exact numeric fidelity, inputs/outputs, comparison tolerances and coverage must be specified.
- Establish a full hardware-in-the-loop (HIL) setup. Firmware must expose UART debug/control through USB, including filesystem operations to load, delete and move .effs and utilities for driving and diagnosing the device. A substantial part must exercise the actual UI through phantom presses, dragging and scrolling, including normal LVGL input handling and callbacks. The firmware owns those command requirements; fixture, transport/protocol details, physical I/O, measurements and acceptance tests remain open.
- Cultivate a broad, good library of verified .eff effects now, aided by DSP and RTL simulation and deployable to the carrier through USB. David is happy with the current ISA, including delay instructions; the earlier instruction-contract blocker is removed. Exact-offset buffer reads are unnecessary. Fractional delay remains a future feature. He has tested current delay modulation for flanging and likes its sound; recommend against long-delay modulation because quantization becomes objectionable. Possible improvement in 24-bit mode is unqualified, not a guarantee. Define coverage and verify authored effects with numerical/audio checks, preserving clear distinctions between model, RTL and physical evidence. Library scale is not fixed. David's request for more interesting effects requires perceptible transformation, beyond basic filter variants and further distortion flavors. His listening feedback finds the deployed wah/vowel barely noticeable and the octave fuzz/drive simply distortion variants; passing model/RTL comparison does not establish satisfaction of this requirement. Include listening and effect-strength assessment in acceptance, with the next library exploration exploiting sample-by-sample arbitrary DSP, including audio-rate cross-modulation, dynamically driven filters, nonlinear feedback and stateful behavior, alongside modulation/time effects. David explicitly emphasizes this device's audio-rate DSP capability rather than conventional effect-category variants. Use no old general-filter instructions for this library; David may revisit that engine on a larger FPGA with 24-bit audio. Current arithmetic/SVF verification and USB deployment are implemented for the first batch; the procedure owner specifies coverage. Broader resource/model/system and physical-audio coverage remain required.

The current carrier has a power constraint reported by David: do not connect the Tang Nano's USB-C while the complete board is externally powered, because the Sipeed board lacks backflow prevention. FPGA flashing is infrequent and can be handled as a separate operation with external board power disconnected. Disconnect Tang USB-C before returning to normal powered operation.

David identifies ESP32 HIL as the routine path for powered testing and diagnostics. Use the MCU UART debug/control connection for .eff filesystem operations and device operation/diagnosis; Tang USB is not required for that loop. The carrier restriction is specific to Tang USB-C and does not block developing ESP32 HIL. This operational guidance does not qualify the future bare-chip board.

Simultaneous external power and FPGA programming is an optional future convenience, not a prerequisite for HIL. If it becomes necessary, qualify a programming path that prevents backfeeding against the exact carrier wiring and USB bridge power requirements before using it. No hardware modification or adapter has been selected.

Existing Core test targets and its full-top WAV harness are implementation evidence, not satisfaction of these requirements. Their owners are in the Core tree at what/do/core/verilator/tests/target.md and how/does/the/full/core/wav/simulation/work.md. The initial firmware UART/phantom-input implementation and its bounded hardware checks belong to the Interface how/to/control/the/interface/over/uart.md leaf.

Next specification work: define how a descriptor is compiled and delivered to each simulator and the device, what observable results are needed, and which automated comparisons and physical measurements constitute acceptance. Keep the occasional FPGA flashing procedure separate from routine ESP32 HIL. David has not supplied a complete test matrix or HIL fixture design.
