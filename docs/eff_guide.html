Kestrel Effect Descriptor Programming Guide

An effect descriptor is the small .eff program that tells Kestrel what an audio effect is: its display name, its front-panel controls, any FPGA resources it needs, and the sequence of DSP instructions that process each sample. You write it as a readable source file; the firmware parser turns compiles the source at boot and uses it to generate the graphical user interface for effects and the machine code for the Kestrel Core.

The system operates primarily using sixteen channels, written c0 through c15, or equivalently c0 through cF. The picture to have in mind is that channels are streams of audio data which flow past a sequence of blocks; each block holds an instruction, and reads, modifies, or writes channels to perform the signal processing. Only c0 flows from one effect to the next; at the start of execution, c0 contains the input sample, and the output should be written to c0, ready for the next effect, or to be sent to the outside world. Channels c1-cF should be used only as memory to use for temporary intermediate values; their contents do not survive through to the next sample. If you need a value to survive from one audio sample to the next, use a resource such as a delay or memory slot, not a spare channel.

The Shape of a Descriptor

Every descriptor starts with the exact version marker v1.0, then a set of named sections. The current parser recognizes .INFO, .RESOURCES, .PARAMETERS, .SETTINGS, .DEFS, and .CODE. The metadata sections are dictionary-like: they contain named entries, strings, expressions, nested dictionaries, and lists. The code section is different: it is an assembly-like list of DSP instructions. During loading, the firmware parses the metadata first, builds a scope of parameters, settings, resources, and helper expressions, and then parses the code against that scope.

On the device, effect descriptor files live on the SD card under /sdcard/eff. At boot, the firmware scans that directory and processes the .eff files it finds there, turning each valid descriptor into an available effect. In normal use, adding an effect means copying its descriptor into that directory and rebooting or otherwise triggering the same effect-loading path.

v1.0

.INFO
name: "Simple Gain"

.PARAMETERS
gain: (
  name: "Gain"
  default: 1
  min: 0
  max: 2
)

.CODE
mul c0 [gain] c0

Entry syntax is deliberately plain. A named value can use either : or =, strings are wrapped in double quotes, and nested dictionaries use parentheses. New lines usually separate entries, though commas are also accepted. Names are identifiers: letters and underscores are accepted, and digits are accepted after the first character. In practice, use lowercase names such as gain, delay_time, or tone_cutoff, because those names become the handles you use later in expressions and code.

Expressions

Most numeric fields are expressions, not just literals. The expression parser accepts decimal numbers, binary and hexadecimal numeric forms, parentheses, unary minus, references by name, and the operators +, -, *, /, and ^. It also accepts common math functions including abs, sqr, sqrt, exp, ln, log, log10, sin, cos, tan, sinh, cosh, tanh, asin, acos, atan, and erf. A reference can point to a parameter, a setting, a definition, a memory slot, or an LFO, provided that thing has already been added to the effect scope.

The firmware provides useful constant expressions internally, including pi, e, sample_rate, freq_max, and related values used by the filter coefficient builders. For authoring, the most useful habit is to put repeated formulas in .DEFS. Definitions are parsed after parameters and settings have entered scope, so a definition can be written in terms of controls such as cutoff, gain, or depth, and then reused in resources or code expressions.

.DEFS
wet: mix
dry: 1 - mix
cutoff_octave_up: cutoff * 2

.INFO

The .INFO section is mandatory. It must contain name, a string shown as the effect name. It may also contain cname, the ``code name'', which is used internally to refer to the effect (i.e., a preset uses the cname of its effects to find the .eff file on disc at boot). If cname is omitted, the parser derives one from name by lowercasing capital letters and turning spaces into underscores.

.PARAMETERS

Parameters are the continuous controls the player adjusts on the effect page: gain, cutoff, feedback, mix, depth, rate, and so on. Each entry in .PARAMETERS is a nested dictionary. The entry name is the internal handle used in expressions and code, while the required name field is the display label. The current extractor requires name, default, min, and max. The default must be a constant expression; the range endpoints may be expressions, which lets one control bound depend on another if the UI behavior needs it.

FieldUse
nameRequired display label string.
defaultRequired constant expression used as the initial value.
min, maxRequired expressions defining the control range.
scaleOptional "linear", "log", or "logarithmic".
unitsOptional display units, such as "Hz", "ms", or "%".
widgetOptional "dial"/"pot", "slider"/"hslider", "vslider", or "vslider_tall".
groupOptional constant integer used by the effect view grouping logic.
max_velocityOptional positive constant expression limiting how quickly the value may move.
driverOptional reference naming a scope entry that can drive the parameter.
 
.PARAMETERS
cutoff: (
  name: "Cutoff"
  default: 1200
  min: 20
  max: freq_max
  scale: "log"
  units: "Hz"
)

mix: (
  name: "Mix"
  default: 0.5
  min: 0
  max: 1
  widget: "slider"
)

.SETTINGS

Settings are discrete controls rather than smooth parameters. The current extractor requires name, type, default, min, and max. Accepted types are "int", "bool", and "enum"; accepted pages are "main" and "settings". In the current code, integer and boolean settings are the safest choices. The parser accepts an options dictionary for enums, but the extractor marks that area as unfinished, so treat custom enum option lists as a future-facing feature rather than the comfortable path today.

.SETTINGS
mode: (
  name: "Mode"
  type: "int"
  default: 0
  min: 0
  max: 2
  page: "settings"
)

bypass_tone: (
  name: "Bypass Tone"
  type: "bool"
  default: 0
  min: 0
  max: 1
)

.RESOURCES

Resources are named pieces of FPGA-side or firmware-managed DSP support that an instruction can use later. Each resource is a nested dictionary with a required type. The current resource extractor recognizes "delay", "mem", "filter", "lpf", "hpf", "bpf", "polynomial", and "lfo". In .CODE, resources are referenced with a dollar sign, as in $delay_line or $tone_filter.

A delay resource must specify exactly one delay amount. The comfortable current spellings are delay, delay_seconds, and delay_samples. In the extractor, delay is treated as milliseconds, delay_seconds as seconds, and delay_samples as samples; size may also be supplied as an expression if the buffer size should be made explicit. The code also checks for a delay_ms spelling, but that path is not handled cleanly later in the same extractor, so prefer plain delay for millisecond delay controls.

.RESOURCES
echo: (
  type: "delay"
  delay: time_ms
  size: 1000
)

Filter resources can be declared either by supplying coefficients yourself or by asking the descriptor compiler to build common biquad coefficients. A generic filter resource requires a coefs list and may specify feed_forward or feed_back. A low-pass or high-pass resource uses type: "lpf" or type: "hpf" with a required cutoff expression and an optional Q. A band-pass resource uses type: "bpf" with required center and optional Q. The default Q is the familiar Butterworth-ish sqrt(2) / 2 value from the firmware constants.

.RESOURCES
tone: (
  type: "lpf"
  cutoff: cutoff
  Q: resonance
)

custom_filter: (
  type: "filter"
  coefs: { b0, b1, b2, a1, a2 }
  feed_forward: 3
  feed_back: 2
)

Memory resources use type: "mem" and currently have very little author-facing configuration in the active extractor; they create a named scope entry and can be read or written by mem_read and mem_write. Unlike channels, memory slots are persistent across sample runs: a memory slot contains the last value written to it until another instruction writes a new value. LFO resources use type: "lfo", require frequency or freq, and must be described either by center plus amplitude or by min plus max. Polynomial resources use type: "polynomial" with a coefs list, then the poly instruction evaluates that resource against an input sample.

.RESOURCES
slow_sweep: (
  type: "lfo"
  frequency: rate
  min: 300
  max: 3000
  scale: "log"
)

.CODE

The .CODE section is the sample-processing program. Each nonblank line starts with an instruction name followed by its operands. Channel operands look like c0, c1, and so on, but ordinary mono effects should read from c0 and write their final result back to c0. Expression operands are wrapped in square brackets, for example [gain] or [0.5 * feedback]. Resource operands are introduced with $, for example $echo. The parser checks the number and kind of operands against the FPGA instruction descriptor table, then creates the block list used to program the core.

delay_writevalue $delayWrite a value into a delay resource.

The descriptor compiler also recognizes tanh4 and sin2pi as convenient LUT-backed waveshaping/read instructions with the form input dest. Shift instructions arsh, lsh, and rsh take a b shift dest, where shift is an integer operand. The state-variable filter path is a little different from ordinary one-output instructions: svf triggers the filter computation and stores the low-pass, high-pass, and band-pass results internally instead of writing directly to a channel. The follow-up instructions svf_low, svf_high, and svf_band then move whichever stored result you want into a channel. Running svf again overwrites the stored SVF results.

.DEFS
dry: 1 - mix
wet: mix

.CODE
filter c0 $tone c2
mul c2 [wet] c2
madd c0 [dry] c2 c0

Think of channels as working registers for the effect program. c0 carries the sample you are transforming, and later channels can be used as scratch space when an effect needs intermediate values. Keep the code easy to audit: move or compute an intermediate into a spare channel, name repeated formulas in .DEFS, then combine the final result back into c0. The compiler will compute the register formats needed for expressions and instruction operands, so the descriptor can stay focused on the signal flow.

A Complete Small Effect

This example is a simple mono low-pass filter with cutoff and resonance controls. It demonstrates the usual descriptor pattern without any special waveshaper behavior: declare friendly controls, create a generated filter resource, process c0 through that resource, and leave coefficient generation and fixed-point scaling to the compiler.

v1.0

.INFO
name: "Simple Low Pass"

.PARAMETERS
cutoff: (
  name: "Cutoff"
  default: 1200
  min: 20
  max: freq_max
  scale: "log"
  units: "Hz"
  widget: "dial"
)

resonance: (
  name: "Resonance"
  default: 0.707
  min: 0.5
  max: 4
  widget: "dial"
)

.RESOURCES
filter: (
  type: "lpf"
  cutoff: cutoff
  Q: resonance
)

.CODE
filter c0 $filter c0

A More Advanced Example: 3-Band EQ

A descriptor can also build a larger signal path out of several filters and a few accumulator instructions. This three-band equaliser splits the mono input into bass, mid, and high bands, applies a dB gain control to each band, and sums the result back into c0. The bass band is made with cascaded low-pass filters, the upper path is made with cascaded high-pass filters, and the mid/high split happens at a second crossover. The gain expressions use the standard dB-to-linear conversion 10^(dB/20).

v1.0

.INFO
name: "3-Band Equaliser"

.PARAMETERS
bass: (
  name: "Bass"
  default: 0
  min: -12
  max: 12
  widget: "vslider_tall"
  units: "dB"
  group: 2
)

mids: (
  name: "Mids"
  default: 0
  min: -12
  max: 12
  widget: "vslider_tall"
  units: "dB"
  group: 2
)

high: (
  name: "High"
  default: 0
  min: -12
  max: 12
  widget: "vslider_tall"
  units: "dB"
  group: 2
)

.SETTINGS
low_co: (
  name: "Bass Crossover"
  type: "int"
  default: 250
  min: 30
  max: 22000
  group: 0
  page: "main"
)

high_co: (
  name: "Treble Crossover"
  type: "int"
  default: 1000
  min: 30
  max: 22000
  group: 1
  page: "main"
)

.RESOURCES
LP1: (type: "lpf", cutoff: low_co,  Q: 1/sqrt(2))
LP2: (type: "lpf", cutoff: low_co,  Q: 1/sqrt(2))
HP1: (type: "hpf", cutoff: low_co,  Q: 1/sqrt(2))
HP2: (type: "hpf", cutoff: low_co,  Q: 1/sqrt(2))
LP3: (type: "lpf", cutoff: high_co, Q: 1/sqrt(2))
LP4: (type: "lpf", cutoff: high_co, Q: 1/sqrt(2))
HP3: (type: "hpf", cutoff: high_co, Q: 1/sqrt(2))
HP4: (type: "hpf", cutoff: high_co, Q: 1/sqrt(2))

.CODE
filter c0 $LP1 c1
fcasc     $LP2 c1
filter c0 $HP1 c2
fcasc     $HP2 c2
fcasc     $LP3 c3
fcasc     $LP4 c3
filter c2 $HP3 c4
fcasc     $HP4 c4

macz c1 [10^(bass/20)]
mac  c3 [10^(mids/20)]
mac  c4 [10^(high/20)]

mov_acc c0

Working Method

Build effects in passes. First write .INFO and the parameters, then load the descriptor and confirm that the controls appear with sane ranges. Next add resources and a minimal .CODE path that passes audio or applies one obvious operation. Only then add feedback, filtering, modulation, or waveshaping. Parser errors are usually literal: a missing mandatory attribute, a wrong value type, an unknown resource, an unsupported field name, or an instruction with the wrong number of operands. When in doubt, simplify the descriptor until it loads, then add one idea back at a time.

Current-code notes. This guide is based on the parser, extractors, scope code, and FPGA instruction descriptor table in the firmware, not on the older descriptor files that may still be present in the tree. A few recognized features are visibly unfinished or rough in the current code, especially enum option extraction and some memory-resource configuration. The comfortable authoring path today is parameters, definitions, delay resources, generated filters, polynomial resources, SVF where its three-output model is useful, and the ordinary arithmetic/resource instructions.

Author Checklist

Start the file with v1.0. Include .INFO with a string name. Give every parameter a display name, constant default, and range. Keep internal names simple and stable. Put repeated formulas in .DEFS. Declare resources before using them in .CODE. Wrap runtime expressions in square brackets inside code. Prefix resources with $. Prefer a small working descriptor over a clever first draft, because most effect ideas become easier once the basic signal path is already running.
